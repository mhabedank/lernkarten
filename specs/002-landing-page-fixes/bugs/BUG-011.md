# Bug Report: The nav links hang from the top of the bar, and two sections leave a column of dead space

**Type**: Implementation drift (S1) + Spec gap (S2, S3)
**Severity**: High — S1 is a visible regression in the one element present on
every screen of the page; S2 and S3 are Medium.
**Feature**: 002-landing-page-fixes (`docs/index.html`)
**Reported**: 2026-09-08
**Status**: Patched — S1 only
**Patched**: 2026-09-08
**Split**: S2 and S3 are tracked as [#104](https://github.com/mhabedank/lernkarten/issues/104); this report keeps them for the trace, and only S1 is patched into 002.

## Description

Three symptoms, reported together, in `docs/index.html` above the mobile
breakpoint.

### S1 — the nav links are flush against the top of the bar

The four links (`how it works`, `the card`, `printing`, `install`) sit at the
top edge of the sticky bar instead of on its vertical centre line. `lernkarten`
on the left and `github` on the right are still centred, so the bar reads as
three items on two different baselines. The reporter notes this is **new** — it
was not there before.

It is a regression from this feature. Commit `fd7e791` (T009/T011, US1) wrapped
the link row in a `<details>`:

- **Before** (`fd7e791^:docs/index.html:99-101`) `.nav__links` was a direct
  flex child of `.nav`, and it declared `flex: 1`. `.nav` is
  `align-items: stretch` (`docs/index.html:98`), so the row stretched to the
  bar's full height and its own `align-items: center` had a full-height box to
  centre the links in.
- **After** (`docs/index.html:112-120`, `347-351`) `flex: 1` moved to
  `.nav__menu`, the `<details>`. The details stretches to the bar's height, but
  it is a block container: `::details-content` and `.nav__links` inside it are
  auto-height and hug their content, so the row sits at the top of the stretched
  box and `align-items: center` on `.nav__links` centres the links inside a box
  that is only as tall as the links. The bar's height comes from `.nav__home`
  (`docs/index.html:102-106`, 22 px display type + 14 px padding), which is
  taller — that difference is the gap the reporter sees.

Nothing in the feature's test suite or its by-hand checklist could catch this:
A1–A3 (`tests/test_landing_page.py:215-259`) are structural assertions about
`overflow-x`, the `<summary>` text and which links sit inside the disclosure.
None of them is about the desktop rendering.

### S2 — `03 print it, cut it` has a tall empty column

`.print` (`docs/index.html:240`) is a two-column flex row, `align-items: stretch`.
Measured in headless Chrome at 1280 px, both columns are drawn 1176 px tall:

| column | contents | ink |
|---|---|---|
| `.print__rules` (420 px, `:252`) | three `.rule-item` (192 + 120 + 120), `.print__cut` (332), `.print__box` (410) | **1174 px** — packed to the pixel |
| `.print__sheets` (860 px, `:241`) | two labels (18) + two `.sheet__page` (297, fixed) | **327 px** |

The right column carries 3.6 × the left. Below the sheets sit **809 px (69 %)**
of empty `--ground`. The figure is identical at 1120, 1280, 1440 and 1800 px —
`.shell` caps the content at 1280 px, so this is the layout, not a narrow window.

Note for whoever fixes it: `.sheet` is *already* stretched to 1096 px by the
default `align-items: stretch`, while the visible `.sheet__page` inside stays
297 px. The empty area is inside the `.sheet` boxes, not beside them.

The imbalance was not designed; it accreted. `.print__rules` gained content from
three later features after this one shipped, none of which re-measured the
column against `.print__sheets`:

| Feature | Task | What it appended to `.print__rules` |
|---|---|---|
| 007-card-box | T010, T012 | the whole `.print__box` — heading, paragraph, download link, sizing note |
| 008-leitner-compartments | T054 | the `--dividers 4` paragraph and the `leitner.html` link |
| 009-a8-default-grid | T018 | rewrote the cutting rule, the SVG and the margin paragraph |

### S3 — `02 one card, one idea` has the same shape

`.anatomy` (`docs/index.html:220`) is a `1.2fr / 1fr` grid. The right cell holds
four `.anatomy__item` blocks measuring 156 + 156 + 180 + 154 = **646 px**
(`:602-618`); the left cell holds cards of a fixed `height: 269px` (`:165`).

**This feature caused S3, deliberately and without noticing.** Commenting out
`back.hidden = true` (`:796`) and measuring both states at 1440 px:

| state | visible cards | left-cell ink | dead space |
|---|---|---|---|
| JavaScript off — both cards | 2 | 604 px | **40 px** — the cell's bottom padding, i.e. none |
| JavaScript on — today | 1 | 269 px | **335 px (52 %)** |

Two cards at 269 px plus the 26 px gap plus 80 px padding come to 644 px, which
is exactly the height the four prose items set. The left column was balanced
*because* it held two cards. Making `[hidden]` effective (`:331`, `:796`) left
one — correctly, per SC-005 — and the other half became a hole. SC-005 asserts
the halving as correct behaviour; nothing asserts anything about the space it
frees.

## Artifact Traceability

### spec.md

- **Affected user story (S1)**: User Story 1 — *Every nav link is reachable on a
  phone* (`spec.md:43`)
- **Affected requirement (S1)**: **FR-005** (`spec.md:252-253`) — *"Above the
  mobile breakpoint the navigation MUST be visually unchanged from today."*
  This is the requirement the bug violates outright. The bar above 760 px is
  **not** what it was before the change: the link row lost its vertical
  centring. FR-005 is the only requirement in the feature that governs desktop
  nav rendering, and it is a prose obligation with no assertion and no
  measurable success criterion behind it.
- **Affected user story (S3)**: User Story 3 — *"show the back" turns the card
  over* (`spec.md:173`), and **SC-005** (`spec.md:376-377`).
- **Gap identified (S2, S3)**: no requirement in this spec — nor a rule in
  `docs/design.md`, nor a clause in constitution XVI — says anything about what
  happens when one column of a two-column section is much shorter than the
  other. Every rule about the landing page's layout is about *rules and type*:
  the 15 px floor (SC-010), the band heights (SC-003, FR-006–FR-008), single
  borders (FR-009). Vertical balance is unspecified, so no gate can fail on it
  and content can be appended to a column indefinitely.
- **Note on scope**: US3's *"Scope decision, already taken"* (`spec.md:191-196`)

  that same decision, so it has to be reopened rather than assumed.

## Root Cause Analysis

**S1 is implementation drift with a missing gate.** The `<details>` wrapper was
the right answer to US1's real problem, but wrapping a flex item in a block
container silently drops the stretched height on the floor. That is a known CSS
trap, and the feature already hit its neighbour once — the comment at
`docs/index.html:340-346` records how `::details-content` had to be overridden
because overriding the panel's own `display` "looks like it works (the computed
value even reads `flex`)". The same class of failure recurred one property over,
on height instead of display, and this time nothing caught it: FR-005 says
"visually unchanged" and *visually unchanged* is not something A1–A3 can assert.
The requirement was carried entirely by by-hand rows T036 and T039, which are
the two rows in the feature most dependent on remembering what the page used to
look like — and the "before" was already committed and gone by the time they ran.
Constitution XI permits the manual split for layout work only if the manual
claims are named; they were named, and they still did not hold.

**S2 is accretion without an owner.** No single commit made the print column
lopsided. 007-card-box, 008-leitner-compartments and 009-a8-default-grid each
appended a correct, well-scoped piece of content to `.print__rules`, and each was
reviewed against its own spec. Nothing in the repository measures a section's two
columns against each other, so there was no gate to trip and no reviewer whose
job it was to look.

**S3 is a side effect of a fix, unmeasured.** Making `[hidden]` effective was
right and SC-005 is right. It also removed half the left column's content on
every JavaScript-enabled visit. The spec reasoned about the toggle's *behaviour*
and never about the *layout* the working toggle leaves behind — which is the same
blind spot as S2, reached from the other direction.

The common thread: this repository's landing-page gates check **type size,
structure, rules and copy**. Nothing checks **proportion**. All three symptoms
live in that gap.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to update the spec artifacts:
   - **S1** — the smallest correct change is to let the bar's height reach the
     link row: give `.nav__menu` and `::details-content` a `display: flex` in the
     `min-width: 761px` block so the stretch chain is unbroken, rather than
     hard-coding a height on `.nav__links`. Reopen T011, T014, T036 and T039;
     add the missing red assertion and the compare-against-the-parent-commit row.
   - **S2 / S3** — **out of scope here, filed as
     [#104](https://github.com/mhabedank/lernkarten/issues/104)** with the
     measurements above. Re-proportioning a section is a design change under
     constitution XVI, `02`'s remedy is the undecided half of #28, and patching
     either into a closed feature would repeat the accretion that produced S2.
     This patch therefore touches S1 only.
2. Run `/speckit.bugfix.verify` to confirm the patched artifacts are consistent.
3. Resume `/speckit.implement` for the S1 code fix, test-first per constitution XI:
   write the assertion, watch it fail on the current file, then fix the CSS.
