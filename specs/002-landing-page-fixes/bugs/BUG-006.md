# Bug Report: The landing page sets running prose below the 15 px floor that the design doc and constitution XVI both state

**Type**: Spec conflict
**Severity**: Medium — nothing is broken on screen; a contributor who follows
the rule the constitution requires them to read finds the page does not keep it
**Feature**: 002-landing-page-fixes
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19
**GitHub issue**: [#30](https://github.com/mhabedank/lernkarten/issues/30)

## Description

`docs/design.md:55` states a floor, without qualification:

> Reading text is never smaller than 11 pt printed or **15 px on screen**.

`docs/design.md:142` treats it as a constraint worth paying for — the landing
page sets the command at 16 px rather than 18 px specifically "to buy the room
that keeps the caption at 15 px, the floor above". Constitution XVI repeats it
as a principle.

`docs/index.html` sets Archivo running prose in `--muted` below that floor in
four places:

| Line | Selector | Size | Text |
|---|---|---|---|
| 93 | `.band__note` | 14 px | the note under every section band (3 instances) |
| 226 | `.anatomy__item p` | 14 px | the descriptions in the card anatomy list |
| 257 | `.print__cut p` | 13 px | the descriptions in the printing section |
| 624 | inline `style` | 14 px | "One file per topic. If a card is wrong, you fix a line…" |

All four are full sentences of prose. None is a label.

**Not in scope, and worth stating so nobody widens this**: the page also sets
10–13 px in places that are *not* reading text and should stay as they are —
uppercase `label` runs in Jost 500 (`.nav__links`, `.toggle`, `.step__optional`,
`.anatomy__key`) and IBM Plex Mono literals (`.hero__facts`, `.step__writes`,
`.card__source`, `.install code`, `.tree`). `docs/design.md` gives those faces
their own rows, and its floor sentence says *reading text*.

## Why this is a conflict rather than a gap

This feature's own spec takes **both** positions, in two places, and that is the
defect:

- **FR-015** (`spec.md:275`) — "Every change MUST hold to the design rules …
  reading text never below 15 px".
- **FR-011** (`spec.md:265`) — "Note type size MUST stay at its current 14 px."
- *Edge Cases* (`spec.md:228-231`) — "the existing note at 14 px is **not**
  reading text under that rule — it is a secondary annotation in `--muted`".
- *User Story 2* (`spec.md`, the rejected-fixes list) — "The note is already at
  14 px, which is **itself below that floor** … the correct direction for the
  type size is up".
- *Print & Design Impact* (`spec.md:296`) — "**Minimum type size respected**:
  yes".

So one spec says the note is exempt, says it is in breach, and then certifies
the feature as compliant. Each statement was defensible when written and they do
not survive being read together. Deferring the size to #30 was the right call
for that feature; leaving three contradictory readings of the rule behind was
not.

## Root Cause Analysis

A **spec conflict** produced by a rule that was written for one medium and
inherited by another. "Reading text is never smaller than 11 pt printed or 15 px
on screen" was written about the card, where every word is reading text and the
reader is holding a piece of paper. On a landing page there is a whole register
between reading text and a label — annotations, captions, footnotes — and the
rule has no vocabulary for it. So each contributor decides for themselves, and
this feature's spec shows one contributor deciding three different ways within
one document.

The reason it survived to a released page is that the floor is prose in a design
document and nothing else. There is no check. `tests/test_landing_page.py`
asserts structure — an element, an attribute, a rule's presence — and type size
is just as assertable as any of them, but nobody was asked for it because the
rule lives somewhere no test reads.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to supersede FR-011, resolve it against FR-015,
   and add the tasks.
2. Run `/speckit.bugfix.verify`.
3. Resume `/speckit.implement`: the failing type-size assertion first, then the
   four declarations, then the scoping sentence in `docs/design.md` and
   constitution XVI.

**Recommended resolution: the page is wrong, raise the four.** The issue frames
this as an open choice between the page being wrong and the rule being too
absolute, and when it was filed both were live. The plan section above closes
it: the one concrete cost of raising them — taller section bands — was removed
by feature 002 three days ago, so the cheap option no longer has a price. And
of the two, only "raise the page" leaves a rule a test can enforce; "scope the
rule" leaves the same argument to be had again by the next contributor. The
scoping sentence is still worth writing, but as a statement of which *faces* the
floor covers (Archivo prose yes, Jost labels and Plex Mono literals no), not as
a licence for prose to sit below it.
