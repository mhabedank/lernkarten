# Bug Report: A counted front does not force an enumerated back, and a list past four items has nowhere to go

**Type**: Spec gap, with a spec conflict underneath
**Severity**: Medium
**Feature**: `feat/deck-anchors` (specs/007-deck-anchors), shipped in v0.9.0
**Reported**: 2026-09-07
**Source**: GitHub issue [#83](https://github.com/mhabedank/lernkarten/issues/83)
**Status**: Half fixed — E-1 shipped, E-2 to E-4 open
**Fixed**: 2026-09-07 — E-1 and the four-item cap, PR
[#96](https://github.com/mhabedank/lernkarten/pull/96), branch
`fix/counted-front-enumerated-back` (`2d9383b` red, `6760beb` the check,
`1371542` the prose). See [What shipped](#what-shipped) at the end.

**Numbering**: BUG-009 continues the project-wide sequence (BUG-001 to BUG-008
are referenced from `tests/test_check_project.py`,
`tests/fixtures/demo-project/broken/README.md` and `docs/testing.md`).

**Filed against 007-deck-anchors, not against the current feature directory**
(`.specify/feature.json` points at `specs/010-machine-settings`, which this bug
does not touch). 007-deck-anchors owns the one rule this repo has about a
`#list([…])` back — A-2, FR-012/FR-013 — and the fix has to be designed
against it, because the two rules meet in the same place. Same placement
rule BUG-008 followed.

## Description

A front that announces a count — *"What are the four types of work?"* — is a
promise about the shape of the back. Nothing in the pipeline holds the back to
that promise, and nothing tells an enumeration longer than four items where to
go.

Two halves, and they feed each other:

**Half 1 — the promise is not kept and not checked.** No rule anywhere says
*when* a back has to be an enumeration. `skills/cards/SKILL.md:222` mentions
`#list` only as syntax, one item in a list of Typst markup next to `$…$` and
the line break; `CLAUDE.md:92` does the same. The one *rule* about lists is the
A-2 orphan rule (`skills/cards/SKILL.md:224`), which constrains what a list's
items must be anchored by and says nothing about whether the back is a list at
all. `scripts/check_project.py` has **no check that reads a front and its back
together** — every card-level check in `check_cards` is per face (budget, image
path, id) and the two cross-card checks (`_check_anchors:847`,
`_check_orphans:808`) never look at a front-to-back relationship.

So a generated card can promise *n* items and deliver a paragraph, and the
cheap deterministic case — front says four, back is a `#list` with three — is
not caught either:

```yaml
front: 'What are the four types of work in the research phase?'
back: '#list([Customer interviews], [Behavioural analysis], [Process mapping])'
```

Nothing in the repo notices. `_list_items` (`scripts/check_project.py:163`)
already extracts the items by a bracket-depth scan, so the count is available;
nobody compares it to the front.

**Half 2 — the four-item cap is wrong.** `skills/cards/SKILL.md:222` caps
`#list` at four items. Real material has six-step processes and ten-item
checklists, and the number is frequently the point. The cap does not make such
a card readable — it makes the rule inapplicable, so the card is written as
prose and lands back in half 1. The repo's own fixture already contradicts it:
`tests/fixtures/demo-project/cards/geography.yaml:7-8` (card `Y4H26`) asks for
five islands and lists five, and it is right. Splitting is not free either:
"name the six steps" cannot become two cards of three without destroying the
skill the card tests.

Evidence from a real deck is in the issue — two cards, both well-formed, both
under budget, both passing `lernkarten check` and `check_project.py` today
(`B7SGP`, a counted front with a prose back carrying a second fact; `N6JZP`, a
double question that *forces* the prose back and makes the count unrecoverable).
They stay in the issue: the demo project is subject-agnostic and invented, per
the repo rule, so its failure modes have to be rewritten in its own subject.

## Artifact Traceability

### spec.md (specs/007-deck-anchors)

- **Affected user story**: **US2 — A-2 (orphan)**, P1. It is the only story in
  the repo about `#list([…])` backs. It asks *"is every item this list
  enumerates taught somewhere else?"* and never *"should this back have been a
  list, and does it have the right number of items?"*
- **Affected requirements**:
  - **FR-012 / FR-012a / FR-013 / FR-013a** — A-2 and its normalisation. All
    correct as written and all downstream of an assumption never stated: that
    a `#list` is *input*, something the model already decided to write. The
    requirement that would have made that decision checkable does not exist.
  - **FR-014 / FR-014a** — message shape. Any new check has to match it:
    `card {i}` by 1-based index, never the `id`, plus an em-dash reason clause.
  - **FR-015** — both checks are errors. This is where the fix gets sharp: E-1
    (count mismatch) is as deterministic as A-2 and can be an error; E-2/E-3/E-4
    involve judgement and cannot.
  - **FR-017** — pure-Python text analysis, no new dependency, no network. A
    number-word table is in scope under this; anything needing a language model
    is not.
  - **FR-025 / FR-026** — `/cards` runs `python3 scripts/check_project.py .` as
    a numbered step. Whatever E-checks are added are reported through that step
    and need reactions written into `skills/cards/SKILL.md:40-52` beside the two
    that are there.
- **Affected success criterion**: **SC-002** — "on a card file with *k* list
  members, the checker reports exactly the members named by no other card". It
  measures membership and never arity. **SC-001** matters for the fix, not the
  bug: the demo project must stay at zero errors *and zero warnings* under
  `--strict`, so every new advisory has to be satisfiable by the fixture.
- **Gap identified**: the spec has a rule for *what is inside a list* and no
  rule for *whether there is a list*. The front — the half of the card that
  makes the promise — is not read by any requirement in this feature.

### The conflict with A-2 (the reason this is not a one-line patch)

A-2 is shipped, and it is an **error**. This bug's fix pushes prose backs
*into* `#list([…])` form, and every item so created immediately falls under
A-2: it must be named by another card in the same file or the build fails.
Following the new rule can therefore break a deck that passes today. The
issue's tiered proposal resolves this at the top end by construction — the 9+
tier's per-group cards anchor their own members — and leaves the 3–8 tiers
exposed. Both rules are right; they want designing together, which is the
issue's own conclusion and is why this report lands on 007-deck-anchors.

## Root Cause Analysis

**Three causes, stacked.**

1. **The cap was never a decision.** `at most 4 items` entered in `0e19c8c`
   (the English relaunch) as a parenthetical inside a Typst syntax note and was
   carried forward unexamined through `e164daa`. It predates the grid work and
   the anchor work, so no feature ever had reason to re-derive it — and a number
   that arrived as an aside is exactly the kind that is never revisited.
2. **007-deck-anchors specified the inside of the list and stopped there.** The
   feature was framed by issue #49 — terms the deck argues about but never
   names — so it asked what list *items* must be anchored by. Its checks read
   `front + " " + back` as one haystack (`_check_orphans:827`,
   `anchor_text` at `:1006`), which is right for *mentioning* and structurally
   blind to the front making a *promise* about the back. Nothing in the feature
   pointed at the arity question, so nothing declined it either.
3. **Convention with nothing behind it survived in the fixtures.** Both
   enumerations in this repo — `4V946` and `Y4H26` — happen to keep their
   count, so every gate is green and the rule looks enforced. This is the same
   failure shape as BUG-008: a fixture that shares the good behaviour of the
   thing it stands in for cannot show the rule is missing.

## Recommended Fix

The design questions the issue leaves open are load-bearing and there are
seven of them — tier boundaries (item counts or a measured budget), what
"chunked" means to a checker, whether the 9+ split keeps the count honest,
number words per `language:`, whether "name the …" without a numeral counts,
the interaction with A-2, and whether the moved elaboration pushes a subtopic
past the 3–8 card budget. That is a **new feature spec** (`011-…`) that amends
007-deck-anchors, not a `/speckit-bugfix-patch` to it. The one part that is
already decided is E-1.

1. `/speckit-specify` from issue #83 for the tiered rule and the E-checks —
   or `/speckit-bugfix-patch` on 007-deck-anchors if the scope is cut to E-1
   plus removing the cap, which is the shippable half.
2. `/speckit-clarify` on the seven open questions; the A-2 interaction and the
   number-word table decide how much of the bug E-1 can catch at all.
3. `/speckit-bugfix-verify` for consistency across artifacts.
4. `/speckit-implement`, red tests first.

**If only one thing ships**: E-1 plus deleting the cap. E-1 is fully
deterministic, has zero false positives by construction (it fires only when a
numeral in the front and a `#list` in the back disagree), reuses `_list_items`,
and can be an error under FR-015. The cap is demonstrably wrong and its removal
costs one line. E-2 through E-4 need the tier design and the A-2 resolution
first.

## What shipped

PR #96 took the deterministic half, exactly as this report's last paragraph
scoped it, and nothing beyond it.

**E-1 (mismatch)** — `_check_counts` in `scripts/check_project.py`, an
**error** beside A-1 and A-2 under FR-015. It fires only where a numeral in the
front and a `#list([…])` in the back disagree. Message, per FR-014's shape:

```
card 1: the front announces 'four' and the back enumerates 3 — a counted front
is a promise about the back, and the learner grades against it
```

**The four-item cap is gone** from `skills/cards/SKILL.md`, replaced by a rule
where a rule belongs rather than a number inside a Typst syntax note: a counted
front gets exactly that many items, no fixed cap, the ~400 character back
budget bounds the length, and "name the six steps" does not become two cards of
three. The rule is also in `CLAUDE.md` § Card style, the reaction to the new
message is step 6 of `skills/cards/SKILL.md`, and the borderline cards are
documented in `tests/fixtures/demo-project/README.md`.

The demo project needed **no card edit**: both enumerations in this repository
already keep their count (`Y4H26` five/5, `4V946` three/3). The red cases live
in `tmp_path`, following T024's precedent.

### Three of the open questions are now answered

- **Number words are language-specific** → they bind to the deck's own
  `language:` rather than being pooled. `elf` is eleven in a German deck and a
  creature in an English one, and a check that reports an *error* cannot afford
  the ambiguity. English and German have tables; every other language is
  checked on digits alone, which is the honest reach of a table nobody has
  written yet.
- **Counting `[…]` items needs a real parse** → it reuses `_list_items`, so the
  Typst fragment is parsed once and A-2 and E-1 cannot drift on what an item
  is. `None` (unbalanced) and `[]` (no enumeration) are both read as "no list
  to count", exactly as A-2 reads them.
- **Whether "name the …" without a numeral announces a count** → for E-1, no.
  With no numeral there is no number to compare, and the card is silent. That
  front is E-2's business, and E-2 did not ship.

Two guards beyond the maths gate keep the false-positive count at zero, and
both were decisions this report did not anticipate: only a **whole token**
counts (`three-body` and `Zwölftelregel` announce nothing), and a front
announcing **two different** counts is left alone, because no rule can say
which number the back answers to. `NKQK0` in the demo project is exactly that
card, and it is silent on purpose.

### What is still open

E-2, E-3 and E-4; the tier boundaries and whether they are item counts at all;
what "chunked" means to a checker; how a 9+ split keeps the count honest;
whether moved elaboration pushes a subtopic past the 3–8 card budget; and the
one that gates E-2 — **the collision with A-2**. A-2 is an error, so a rule
that pushes prose backs *into* lists can turn a green deck red unless every new
item is anchored elsewhere. That is a design question against 007-deck-anchors,
not a patch, and issue
[#83](https://github.com/mhabedank/lernkarten/issues/83) stays open for it.
