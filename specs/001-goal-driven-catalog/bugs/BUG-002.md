# Bug Report: Zotero items sharing a title overwrite each other and are counted as "skipped"

**Type**: Spec gap
**Severity**: Critical — silent data loss on a successful-looking run
**Feature**: 001-goal-driven-catalog (see *Feature attribution* below — the code
is older than every feature spec in this repo)
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19
**GitHub issue**: [#10](https://github.com/mhabedank/lernkarten/issues/10)

## Description

`scripts/zotero_ingest.py` derives the name of the file it writes from the item
title alone:

```python
md = target / f"{slugify(title)}.md"  # scripts/zotero_ingest.py:169
if md.exists() and md.stat().st_mtime >= pdf.stat().st_mtime:
    stats["skipped"] += 1  # scripts/zotero_ingest.py:170-172
    continue
```

A Zotero library routinely holds several items with the same title — duplicates,
two editions, a chapter next to the volume it came from. All of them slugify to
one `<slug>.md`. The first item written wins. Every later one finds a file that
exists and whose mtime is newer than the PDF's, because *this run* wrote it
seconds ago, and takes the incremental-skip branch.

Three things go wrong at once, and each hides the next:

1. **The document is dropped.** No warning, no non-zero exit.
2. **`skipped` is the wrong word for it.** That counter means "already ingested,
   unchanged". Here it means "thrown away".
3. **The condition cannot distinguish the two cases at all**, because the only
   thing it compares is a timestamp. A same-run collision and a genuine re-run
   look identical to it.

## Evidence

From the reporting run: a first `/ingest` into a completely empty
`knowledge/<id>/` reported `14 skipped`. Nothing could have been skipped in the
incremental sense — there was nothing on disk to skip. Fifteen items shared one
title and fourteen were discarded. Across the library sixteen documents would
have been lost this way.

Resolving the collisions afterwards by PDF hash showed the loss was real rather
than cosmetic: twelve were genuine duplicates, **two were substantively
different documents** that happened to share a title with another entry.

The item key needed to tell them apart is already in hand at the point of the
collision — it is written into the frontmatter eight lines later as
`zotero_key: {it['key']}` (`scripts/zotero_ingest.py:192`).

  feature's scope — *Scope in the Pipeline* says "`/ingest` and `/print` are

  `| knowledge/<id>/<doc>.md frontmatter | none — … | — |` (`spec.md:601`). That
  row is where the gap sits. It states the *frontmatter* contract and is silent

  source document**, and therefore that the writer needs a naming rule which

  never read back.

  `knowledge/<id>/<doc>.md` file names must be unique per source document, nor
  what `/ingest` must do when two documents want the same name. Constitution
  Principle I lists the format and says nothing about collisions either.

- **Impact**: no phase of this plan changes. The fix belongs to the
  deterministic half and needs the plan's *two halves* seam only to say which

### tasks.md (`specs/001-goal-driven-catalog/tasks.md`)

  the only task in the feature that touched the ingest path, and it touched
  frontmatter prose, not the script.
- **False completions**: none. No task in any feature ever claimed this.
- **Missing tasks**: the whole fix. Needed:
  - a failing case in `tests/test_ingest_sources.py` — the module
    `docs/testing.md` assigns to "zotero over the stub" — driving
    `scripts/zotero_stub.py` with two items that share a title and asserting
    two files come out, both with their own `zotero_key`

    `<slug>.md` exists and belongs to a different item

  - a `collisions` count in the summary line, so the number is visible

## Root Cause Analysis

A **spec oversight** in the deterministic half, of a kind the format contract
invites: the five formats in constitution Principle I are specified as *shapes
of a file* and never as *invariants over a directory*. "One file per source
document" is an invariant over the directory, so there was nowhere to write it
down, and the writer was left to invent a naming rule on its own. It invented
one that assumes titles are unique.

The reason it reached a user rather than a test is the same shape as
[BUG-001](BUG-001.md) and issue #24: the failure is on the **accepted** path.
Nothing rejects it, the exit code is 0, and the one number that would have shown
it — `skipped: 14` against an empty directory — reads as reassuring rather than
as impossible.

Aggravating: the incremental design makes the bug self-concealing. On the second
run the dropped items are still missing and still counted as skipped, so
re-running does not recover them.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to add the uniqueness requirement to the
   knowledge-store contract and the tasks that carry it.
2. Run `/speckit.bugfix.verify` to confirm consistency.
3. Resume `/speckit.implement`: the failing stub-driven test first, then the
   `<slug>-<zotero_key>.md` fallback, the identity-based skip, the written-this-run
   set and the `collisions` counter.

Open for the patch, not decided here:

- whether a collision should also be printed per item as it happens, or only
  summed at the end
- whether the same uniqueness rule should be stated for the other `/ingest`
  paths (folder, web, image), which are model-driven and derive names in the
  prompt rather than in a script
