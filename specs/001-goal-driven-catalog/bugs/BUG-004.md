# Bug Report: A thin document and a failed extraction are written identically, so `/catalog` has to guess

**Type**: Untested flow
**Severity**: Medium — no data is lost, but form labels and cover pages become
topics and cards
**Feature**: 001-goal-driven-catalog (the `/catalog` half of this is squarely
this feature's; see *Feature attribution*)
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19
**GitHub issue**: [#12](https://github.com/mhabedank/lernkarten/issues/12)

## Description

`extract()` recognises exactly two outcomes (`scripts/zotero_ingest.py:92-116`):

```python
if len(text) < 200:  # no text layer — a scan, which the Read tool can see
    return None, True                              # scripts/zotero_ingest.py:112-113
return text, False
```

Either text came out, or the item is written with `pending: <pdf path>` for the
Read tool to fill in. There is no third outcome for **the extraction worked and
there is genuinely almost nothing there**, which is a normal state for a real
library:

- `machine-learning-mit-python.md` — the Zotero attachment is a one-page cover
  stub, not the book. Extraction complete, source thin.
- `the-value-proposition-canvas-1-pdf.md` — an empty canvas template. The
  "text" is the field labels of a form.

Both had to be annotated by hand so `/catalog` would not read them as broken
extractions.

Worse, the two states are conflated by a single number. A one-page cover stub
with 140 characters of real text falls under the same `len(text) < 200` that
means "this is a scan with no text layer", so it is written as `pending:` and
sent to the Read tool — which looks at it, finds the same 140 characters, and
the next incremental run does it again. A scan and a stub are distinguishable
and the code does not distinguish them: a scan has pages and no text, a cover
stub has one page and some text.

## Feature attribution

Split, and worth naming precisely. The **writing** half is
`scripts/zotero_ingest.py`, which predates every spec (see
[BUG-002](BUG-002.md#feature-attribution)). The **reading** half is
`skills/catalog/SKILL.md`, which this feature rewrote, and the requirement the
bug lands on — FR-009's attachment rule and FR-016's counts — is 001's own. So
unlike BUG-002 and BUG-003 this is not filed under 001 by default: 001 genuinely
owns the half that is wrong about what it reads.

## Root Cause Analysis

An **untested flow**, and a threshold doing two jobs. `len(text) < 200` was
written to answer one question — "did this PDF have a text layer?" — and is
being asked a second one it cannot answer: "is this document worth anything?"
The two have the same symptom (little text) and opposite remedies (look at it
again with a different tool / never look at it again).

The reason it survived the spec is that 001 specified the catalog against a
`knowledge/` directory it assumed was already good. Every acceptance scenario in
US2 begins "Given a project with `goal.md` and ingested knowledge" — the quality
of that knowledge is a precondition, never a variable. So no scenario, no
requirement and no check ever asks what happens when a document is technically
present and substantively empty.

This is the third bug in this batch with the same shape as
[BUG-001](BUG-001.md) and issue #24: nothing fails, so nothing is reported, and
the user finds out downstream — here, when a card asks them to recall a form
label.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to add the yield state to the knowledge-store
   contract and a `/catalog` requirement for what to do with it.
2. Run `/speckit.bugfix.verify`.
3. Resume `/speckit.implement`: the failing stub case first, then the split in
   `extract()`, then the two skills, then the demo document.

Open for the patch, not decided here:

- the marker's spelling and threshold. The issue proposes `content: sparse`
  plus the character count; the count alone is more honest and lets the reader
  set the threshold, but a word is what a prompt can act on
- whether the user confirms the marker so it survives the next incremental run,
  as the issue asks — which is really a question about whether `/ingest` may
  ever read a hand-edited knowledge file back, and that is a contract decision
- whether the same distinction is owed to the model-driven `/ingest` paths
  (folder, web, image), which have no `extract()` and no threshold at all
