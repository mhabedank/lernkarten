# Bug Report: A comma in a topic or subtopic name is parsed as a list separator, so the catalog fails to validate against itself

**Type**: Spec gap
**Severity**: High — a valid catalog is rejected with five misleading errors,
and `/catalog` has been observed silently renaming the topic to get past it
**Feature**: 001-goal-driven-catalog
**Reported**: 2026-08-19
**GitHub issue**: [#24](https://github.com/mhabedank/lernkarten/issues/24)

## Description

`Parents:`, `Related:` and `Also covers:` are comma-separated lists, and
`catalog_names()` splits them on every comma without exception
(`scripts/check_project.py:321-334`):

```python
for part in (line or "").split(","):
```

A topic or subtopic whose **name contains a comma** is therefore torn into
several names, none of which exists anywhere.

The heading itself is fine: `parse_catalog()` takes the whole `##` / `###` line,
so the catalog *reads* correctly. Only the attribute lines that reference a name
by text are affected. The result is a catalog that parses cleanly and then fails
to validate against itself.

## Evidence

Reproduced against the current tree:

```python
>>> import sys; sys.path.insert(0, "scripts")
>>> import check_project as c
>>> c.catalog_names("Tides, currents & winds")
['Tides', 'currents & winds']
```

Two names, neither of which is a topic. End to end, a catalog with

```markdown
## Tides, currents & winds
Also covers: Chart datum

### Rhythm of the tide
References: [a](../knowledge/x/a.md)

## Navigation

### Chart datum
Parents: Navigation, Tides, currents & winds
References: [a](../knowledge/x/a.md)
```

produces **five** errors from that one name, all of them pointing away from the
cause:

```
subtopic 'Chart datum': 'Parents:' names 'Tides', which is not a topic in this catalog
subtopic 'Chart datum': 'Parents:' names 'currents & winds', which is not a topic in this catalog
subtopic 'Chart datum': 'Tides' is listed as a parent but '## Tides' carries no 'Also covers:' line naming it
subtopic 'Chart datum': 'currents & winds' is listed as a parent but '## currents & winds' carries no 'Also covers:' line naming it
topic 'Tides, currents & winds': 'Also covers:' claims 'Chart datum', but that subtopic's own 'Parents:' does not list it back
```

Every one of the five invariants that reads a name — C-1, C-2, C-3 (`Parents:`),
C-4 (`Also covers:`) and C-5 (`Related:`) — is affected, because all five go
through the same splitter.

**The release window named in the issue has closed.** The issue says the defect
is "not yet released" and "best fixed before that branch merges". Feature 001
merged as [PR #32](https://github.com/mhabedank/lernkarten/pull/32) on
2026-08-19 and `0.3.1` shipped after it (`pyproject.toml:3`), so
`catalog_names()` is now in a released version and the fix has to keep every
catalog written against it valid. That rules out changing the separator, which
the issue lists as option 3.

## Root Cause Analysis

A **spec oversight** created by a format decision that was never followed
through. Choosing a comma as the list separator implies one of two things — that
names may not contain commas, or that the parser must be cleverer than `split`.
Neither was written down, so the writer assumed the first and the reader assumed
neither.

The tests did not catch it because they were written from the same assumption as
the code. T059–T063 were genuinely red-first and genuinely good tests; they
simply all used names like `Navigation` and `Chart datum`. A test written by the
person who chose the separator inherits the separator's blind spot.

**Why this is worse than a loud failure**, and the reason it is filed at High:
the bug was found because `/catalog` *noticed and worked around it* — it renamed
the area to drop the comma and told the user afterwards. So the user silently
loses the name they asked for, which is the one outcome a validator exists to
prevent. Had the model not noticed, the five errors above send the reader
hunting for a topic that was never missing.

This is the same shape as [BUG-001](BUG-001.md) and [BUG-004](BUG-004.md): the
model in the loop absorbs the defect and reports it as an aside, so the failure
reaches the user as a small unexplained change rather than as an error.

## Recommended Fix

1. Run `/speckit.bugfix.patch` to state the naming rule in the
   `catalog/topics.md` contract, add the requirement, and reopen T066.
2. Run `/speckit.bugfix.verify`.
3. Resume `/speckit.implement`: the failing `tests/test_check_project.py` case
   first, then longest-known-name matching in `catalog_names()`, then the demo
   catalog and the two prose statements.

Option 1 of the issue is the one to take, and the release fact above now settles
it: matching known names first keeps the format unchanged, keeps every catalog
already on disk valid, and keeps the dangling-name diagnostics C-1 and C-5 exist
for. Option 2 (quoting) is a format change; option 3 (a different separator)
invalidates released catalogs, which constitution Principle I calls breaking.

Open for the patch, not decided here:

- what happens to a name that is *both* a known name and a prefix of another —
  longest-match resolves it, but the rule has to be stated rather than implied
- whether `goal.md` bullets under `## Required topics` need the same treatment.
  `topic_key()` strips punctuation for the drift comparison, so a comma there
  may behave differently again, and the issue flags it explicitly
- whether a dangling name that follows a comma-bearing known name should be
  reported with the original line quoted, since the remainder is now the only
  thing being split blindly
