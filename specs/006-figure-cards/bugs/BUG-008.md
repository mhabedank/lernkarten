# Bug Report: `figures.py fetch` cannot reach 28 % of real-world picture URLs

**Type**: Untested flow (both defects), with a spec gap underneath
**Severity**: High
**Feature**: `feat/figure-cards` (specs/006-figure-cards), shipped in v0.7.0
**Reported**: 2026-08-25
**Status**: Fixed
**Patched**: 2026-08-25
**Fixed**: 2026-08-31 — Phase 11 (T114–T124), branch `fix/fetch-reaches-the-web`

**Numbering**: BUG-008 continues the project-wide sequence. BUG-001 to BUG-007
are already referenced from `tests/test_check_project.py`,
`tests/fixtures/demo-project/broken/README.md` and `docs/testing.md`; starting
this feature's bugs at 001 would collide with them.

## Description

Two defects in `fetch`, measured against a real vault of **851 image URLs**:

| Extension | Count | Today |
|---|---|---|
| `png` | 559 | ok |
| **(none)** | **181** | **rejected** |
| **`avif`** | **53** | **rejected** |
| `jpg` | 36 | ok |
| `jpeg` | 14 | ok |
| `webp` | 3 | ok |
| **Google CDN names** | **5** | **rejected** |
| | **239 rejected** | **28 %** |

The rejected set is not a random slice. It is disproportionately **the diagrams
inside articles** — the Double Diamond from *design-thinking*, the Driver Tree
from *building-an-impact-model* — which are precisely the pictures this feature
exists to put on cards.

### Defect A — no `User-Agent`, so Cloudflare answers 403

`scripts/figures.py:165` builds a bare opener and `:172` sends a bare `Request`.
urllib therefore identifies itself as `Python-urllib/3.x`, which Cloudflare
blocks. Isolated: same URL, same urllib, only the header differs — without a UA
403 Forbidden, with one 200 and 70,158 bytes of `image/png`. Not the network,
not `SameHostOnly`.

### Defect B — the format is decided from the URL path, before the request

`scripts/figures.py:166–169` reads `urlparse(url).path`, takes its suffix and
compares it against `IMAGE_FORMATS` (`:48`) *before any request goes out*.
Reproduced against the shipped code:

```
PASS  name='double-diamond.png'            suffix='png'
FAIL  name='AD_4nXfNOMoqZwu_oaU3'          suffix=''
FAIL  name='AD_4nXfNOMoqZwu_oaU3=s1600'    suffix=''
FAIL  name='driver-tree.avif'              suffix='avif'
FAIL  name='img'                           suffix=''
```

Extensionless URLs are what WordPress serves for everything pasted out of Google
Docs (`lh7-us.googleusercontent.com/…`), and they are the largest bucket at 181.

### The two mask each other

An extensionless URL is refused locally and never reaches the request, so the
403 never fires. Fixing only the UA leaves 28 % unreachable; fixing only the
format check turns those rejections into 403s. Both, or neither.

## Correction to the report: AVIF is **not** readable by the pinned engine

The report assumes AVIF is missing from `IMAGE_FORMATS` by oversight, "obwohl
Typst es lesen kann". Tested against the pinned typst 0.15.1, with a genuine
AVIF (`ftypavif` magic, round-tripped through Pillow):

```
avif : error: unknown image format
webp : (compiles)
```

So AVIF is **correctly absent** from the set that decides what may go on a card,
and its 53 URLs cannot be fixed by widening that constant — doing so would move
the failure from a clear message to an engine error at build time.

### The structural bug underneath both defects

`IMAGE_FORMATS` is doing **two different jobs** with one list:

1. *What can the engine print?* — a property of typst 0.15.1, pinned, and the
   right gate for a picture on a card (`build_pdf.IMAGE_FORMATS`).
2. *What are we willing to download?* — a property of the web, where the answer
   is "anything that comes back as an image".

These were never the same set. `figures.py:47` copied the first for the second,
with a comment saying it is "kept in step" — which is exactly the wrong
invariant. AVIF belongs in the second set and not the first: fetch it, then
either convert it or refuse it **as a card picture**, with a message that says
so.

## Artifact Traceability

### spec.md

- **Affected user story**: US2 — "`/ingest` decides which pictures are worth
  keeping" (P2), acceptance scenario 4: *"a picture that cannot be fetched is
  reported in the summary and the ingest continues"*. The reporting half works;
  the fetching half does not, for 28 % of real URLs.
- **Affected requirements**:
  - **FR-008** — "images on a fetched web page" is materially unmet. The path
    exists and is wrong about which pictures it can reach.
  - **FR-015** — is satisfied in letter (failures are reported and the ingest
    continues) and misleading in practice: the message names a format problem
    for what is a *missing filename*.
  - **FR-016** — adjacent and load-bearing for the fix. Sending an honest
    product token is not "fetching what the rules would not fetch"; pretending
    to be a browser to defeat bot protection would be. The fix must stay on the
    right side of that line.
- **Affected success criterion**: **SC-003** relies on the web path keeping a
  figure. It passes on the demo fixture and would not pass on the vault.
- **Gap identified**: the spec never says *what the web actually looks like*.
  It assumes a URL names its own format, which is true of a local
  `http.server` fixture and false of a CDN.

### plan.md

- **Affected section**: **R3 — "Which picture formats may a card name?"** This
  is where the conflation began. R3 answers a question about the *engine* and
  the answer was then reused for a question about the *network*. R3 is correct
  as written; what is missing is a second decision beside it.
- **Affected section**: **R4** — "what can be checked in Python, and what has to
  be left to the engine". The same reasoning applies one level out: what a
  *response* is can be checked in Python (Content-Type plus magic bytes), and
  should be.
- **Impact**: the Dependency section needs no change for sniffing — stdlib and
  a few magic-byte prefixes. Converting AVIF to PNG *would* need a runtime
  dependency (Pillow is dev-only today) and must clear Principle IV; the
  cheaper option is to refuse AVIF with an honest message and let the user
  convert.

### tasks.md

- **Affected tasks**: **T057** (`test_fetch_uses_the_standard_library`) and
  **T058** (`test_fetch_refuses_a_redirect_off_the_source_host`). Both pass and
  both are green for the wrong reason: the fixture server has no bot protection
  and serves a URL ending in `.png`, so neither defect can appear.
- **False completions**: none. T057 and T058 test what they claim; the claim was
  too narrow.
- **Missing tasks**: a red test per defect —
  1. an extensionless URL that returns `image/png` is fetched and staged with a
     usable name;
  2. a server that 403s a request without a `User-Agent` and 200s one with it;
  3. a URL ending `.png` that returns `text/html` is refused **before** it is
     staged (the honesty the sniffing buys);
  4. an AVIF response is fetched but refused as a card picture, naming the
     conversion rather than claiming it is not an image.

### contracts/figures-cli.md

Documents the extension check as the contract for `fetch`. It has to change with
the code: the contract becomes "the response decides, not the URL".

## Root Cause Analysis

**The fetch path was specified and tested against a fixture that shares none of
the properties of the real web.** `tests/test_figures.py` starts a local
`http.server` that answers every request with a PNG, at a URL ending in `.png`,
with no bot protection and no CDN. Both defects are invisible to that fixture by
construction — not by oversight in writing the tests, but because the fixture
was built to exercise *our* code rather than to imitate the thing our code talks
to.

The AVIF half has a second cause: one constant asked to answer two questions,
with a comment asserting the wrong invariant ("kept in step with
`build_pdf.IMAGE_FORMATS`").

This is the failure mode constitution XI exists to catch, and it did not catch
it — because a passing test against an unrepresentative fixture looks exactly
like a passing test.

## Recommended Fix

**Decide the format from the response, not the URL** — the reporter's proposal,
and it is right:

1. Send an honest `User-Agent` via `opener.addheaders`, so it survives redirects
   (`SameHostOnly` already keeps redirects on the source's host). A product
   token — `lernkarten/0.7.0 (+https://github.com/mhabedank/lernkarten)` — not a
   browser string. Only the empty case is blocked, and FR-016 stays intact.
2. Drop the pre-request extension check. Fetch first, then decide from
   `Content-Type` plus magic bytes.
3. Split the two sets: keep `build_pdf.IMAGE_FORMATS` as *what the engine
   prints*; give `figures.py` its own *what we accept from the network*, which
   is wider and includes AVIF.
4. Name the staged file from the sniffed type, since an extensionless URL gives
   no name to work with — and `place` needs a real extension.
5. Refuse AVIF **as a card picture** with a message that says the engine cannot
   read it and what to do, rather than "not a picture this engine reads".
6. Separate the two messages: "this URL has no filename" is not "this is not an
   image".

Then:

1. `/speckit-bugfix-patch` to update `spec.md`, `plan.md`, `tasks.md` and
   `contracts/figures-cli.md`
2. `/speckit-bugfix-verify` to confirm consistency
3. `/speckit-implement` to apply the fix, red tests first

## Note on the workaround in flight

`curl` + `figures.py place` is sound for the 37 images in the three articles —
`place` reads a local file and sends no request, so neither defect applies. Two
holes to know about:

- **Give the downloaded file a real extension.** `place` reads the suffix, so a
  `curl -o chart` with no extension is refused. Check `curl -sI` for the
  Content-Type and name the file accordingly.
- **Any AVIF among the 37 will be refused by `place`, correctly.** Convert to
  PNG first; the engine cannot print AVIF at 0.15.1.
